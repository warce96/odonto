MLOps - Buenas prácticas, políticas y estructuración de archivos

Documento base para establecer lineamientos iniciales del proyecto MLOps, enfocado en la adopción de buenas prácticas por parte del equipo de Ciencia de Datos, la formalización de políticas de trabajo y la estructuración mínima de archivos para lograr una ejecución reproducible, controlada y escalable.

Objetivo de esta etapa

En esta fase inicial del proyecto MLOps se busca establecer una base técnica y operativa común para el desarrollo, validación y posterior paso de modelos analíticos y de Machine Learning entre entornos.

El foco actual no está en la automatización completa del pipeline, sino en la estandarización del trabajo del equipo, la formalización de entregables y la preparación para una ejecución controlada en servidor.

Principios rectores

Reproducibilidad

Un mismo modelo debe producir resultados consistentes bajo las mismas condiciones de entrada.

Trazabilidad

Todo modelo debe poder asociarse a una versión, responsable, fecha y conjunto de dependencias.

Control

La ejecución en ambientes controlados debe prevalecer sobre prácticas manuales o no auditables.

Separación de ambientes

Desarrollo, validación y producción deben mantenerse formalmente separados.

Estandarización

Todos los proyectos deben seguir una estructura mínima común de carpetas, archivos y documentación.

Escalabilidad

La base definida debe permitir evolucionar a futuro hacia automatización, monitoreo y gobierno de modelos.

Buenas prácticas a ser adoptadas por el equipo de Ciencia de Datos

Desarrollo del modelo

  • Separar claramente el código exploratorio del código de ejecución formal.
  • Evitar dependencias implícitas del entorno local.
  • Documentar supuestos, variables de entrada y salidas del modelo.
  • Nombrar archivos y carpetas con una convención uniforme.
  • Utilizar notebooks para análisis y exploración, pero no como entregable principal de ejecución.
  • Pasar la lógica final a scripts estructurados y reutilizables.

Gestión del trabajo analítico

  • Declarar dependencias en requirements.txt.
  • Controlar versiones del código fuente en repositorio.
  • Evitar cambios manuales no documentados en scripts compartidos.
  • Registrar parámetros y configuraciones relevantes del modelo.
  • Incluir archivos de configuración externos cuando corresponda.
  • Entregar el desarrollo con documentación funcional y técnica mínima.
La buena práctica central de esta etapa es transformar el trabajo analítico en un entregable técnico estructurado, portable y entendible por otros equipos.

Políticas iniciales a adoptar

Política Definición Objetivo
Separación entre desarrollo y ejecución El desarrollo se realiza localmente; la validación y ejecución formal se realizan en servidor. Reducir variabilidad y riesgo operativo.
Prohibición de ejecución directa en producción Ningún modelo deberá ejecutarse directamente en PROD sin haber sido validado previamente. Asegurar control y trazabilidad.
Entregable mínimo obligatorio Todo modelo debe contar al menos con script principal, dependencias y documentación básica. Homogeneizar la entrega técnica.
Control de dependencias No se permitirán librerías no documentadas ni instalaciones manuales fuera del proceso definido. Garantizar reproducibilidad.
Documentación mínima El modelo debe incluir descripción funcional, entradas, salidas y supuestos. Facilitar soporte y continuidad operativa.
Paso controlado entre ambientes Todo paso de DEV a DESA y de DESA a PROD debe gestionarse bajo criterios formales. Fortalecer el gobierno del ciclo de vida.

Estructura recomendada de archivos para el equipo de Ciencia de Datos

Para esta etapa, el equipo de Ciencia de Datos debería adoptar una estructura mínima estándar para proyectos analíticos y de Machine Learning. Los notebooks podrán utilizarse para exploración y análisis, pero la lógica final de ejecución deberá estar contenida en scripts estructurados.

proyecto_modelo/ │ ├── src/ │ ├── main.py │ ├── preprocessing.py │ ├── scoring.py │ ├── functions.py │ └── utils.py │ ├── config/ │ └── config.yaml │ ├── notebooks/ │ └── exploracion_modelo.ipynb │ ├── artifacts/ │ ├── modelo_entrenado.pkl │ └── modelo_entrenado.zip │ ├── data/ │ ├── input/ │ └── output/ │ ├── tests/ │ └── test_basico.py │ ├── requirements.txt ├── README.md └── .gitignore
El objetivo no es complejizar el trabajo del equipo, sino ordenar el proyecto para que pueda ser entendido, validado y preparado para su implementación en ambientes controlados.

Descripción de archivos y carpetas clave

src/

Contiene la lógica formal del desarrollo, incluyendo ejecución principal, preprocesamiento, scoring y funciones reutilizables.

functions.py

Archivo destinado a centralizar funciones de apoyo reutilizables dentro del proyecto.

notebooks/

Espacio para exploración, análisis y prototipado. No debe ser el artefacto principal de ejecución formal.

artifacts/

Carpeta para almacenar artefactos del modelo, como archivos entrenados, serializados o empaquetados en formato .zip.

requirements.txt

Lista formal de dependencias necesarias para ejecutar el proyecto.

README.md

Documento de referencia rápida con propósito, entradas, salidas y forma de ejecución.

Elementos a cargo del implementador o frente técnico

  • Construcción del entorno de ejecución en servidor.
  • Instalación y configuración de Docker en ambiente controlado.
  • Definición y mantenimiento del Dockerfile.
  • Construcción y prueba del contenedor en servidor.
  • Validación técnica del paquete entregado por Ciencia de Datos.
  • Preparación de la base para futuras automatizaciones del pipeline.
En esta etapa, el Dockerfile no forma parte de las buenas prácticas centrales del equipo de Ciencia de Datos, sino del frente implementador o técnico encargado de la ejecución controlada en servidor.

Responsabilidades del equipo de Ciencia de Datos

  • Desarrollar y validar funcionalmente los modelos en entorno local.
  • Estructurar el entregable técnico conforme al estándar definido.
  • Documentar dependencias, supuestos e instrucciones de ejecución.
  • Entregar el modelo preparado para ser implementado y probado en servidor.
  • Corregir observaciones surgidas durante la validación técnica en DESA.
  • Adoptar progresivamente prácticas más cercanas a desarrollo de software productivo.

Responsabilidades del frente técnico / implementador

  • Habilitar Docker en el servidor Ubuntu de validación.
  • Preparar el entorno de ejecución controlado.
  • Construir y ejecutar contenedores en ambiente controlado.
  • Verificar consistencia técnica del entregable.
  • Definir lineamientos mínimos para el paso ordenado entre ambientes.
  • Preparar la base para futuras automatizaciones.

Prácticas no recomendadas en esta etapa

No recomendado:
Ejecutar modelos únicamente desde notebooks sin estructuración del código.
No recomendado:
Utilizar notebooks como entregable principal para ambientes controlados.
No recomendado:
Entregar modelos sin documentación básica ni instrucciones de ejecución.
No recomendado:
Depender exclusivamente del entorno local del analista para ejecutar el modelo.

Evolución esperada en fases posteriores

  • Versionado de modelos con herramientas como MLflow.
  • Versionado de datos y features con DVC o solución equivalente.
  • Automatización parcial o total del pipeline.
  • Monitoreo de desempeño y drift de modelos.
  • Mayor formalización de aprobaciones y paso entre entornos.
Esta etapa inicial sienta la base de orden, control y disciplina técnica sobre la cual podrá evolucionar el frente de MLOps en el futuro.
Conclusión

La adopción de buenas prácticas, políticas mínimas y una estructura estándar de archivos permitirá al equipo de Ciencia de Datos trabajar de forma más ordenada y preparada para un esquema MLOps. El objetivo inmediato es lograr entregables reproducibles, trazables y listos para validación técnica en entornos controlados.
