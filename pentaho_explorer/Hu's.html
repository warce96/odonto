Épica: Proyecto MLOps

Iniciativa orientada a establecer las bases técnicas y operativas para la ejecución controlada, reproducible y trazable de modelos analíticos, mediante Docker y un flujo formal de promoción entre entornos DEV, DESA y PROD.

Instalacion de Docker en server de Validacion y Normalizacion de estructura de Modelos de Ciencias de Datos

Estado sugerido New / To Do
Como equipo técnico,
quiero disponer de Docker instalado y operativo en el servidor de validación, junto con una estructura estándar para contenerizar los modelos analíticos,
para asegurar una ejecución reproducible, controlada y preparada para su promoción entre entornos.

Descripción

Actualmente los modelos analíticos pueden depender de configuraciones locales, librerías no uniformes y diferencias entre ambientes, lo que dificulta su reproducibilidad y su posterior paso a validación y producción. Esta historia busca habilitar la base técnica inicial del proyecto MLOps, dejando Docker instalado en el servidor objetivo y definiendo el empaquetado estándar de los modelos mediante contenedores.

Objetivo

Contar con una plataforma técnica mínima que permita ejecutar modelos de forma consistente en un entorno controlado, evitando diferencias entre desarrollo y validación.

Alcance

  • Instalación y configuración de Docker en el servidor definido para DESA/validación.
  • Validación de ejecución de contenedores en dicho servidor.
  • Definición de estructura estándar mínima para entrega de modelos analíticos.
  • Empaquetado de un modelo base mediante Docker.
  • Documentación técnica del proceso de instalación, build y ejecución.

Fuera de alcance

  • Automatización completa del pipeline CI/CD.
  • Implementación de MLflow, DVC o monitoreo de modelos.
  • Despliegue productivo definitivo.

Criterios de aceptación

  • Docker queda instalado y configurado correctamente en el servidor definido para DESA/validación.
  • Se valida que el servidor puede construir y ejecutar contenedores sin errores.
  • Se define una estructura estándar mínima de entrega del modelo analítico, incluyendo al menos modelo.py, requirements.txt y Dockerfile.
  • El modelo puede empaquetarse y ejecutarse exitosamente mediante Docker en el servidor.
  • La ejecución del contenedor produce resultados consistentes ante las mismas entradas de prueba.
  • Las dependencias del modelo quedan formalmente declaradas y controladas.
  • Se documenta el proceso técnico de instalación, construcción y ejecución del contenedor.

Dependencias

  • Disponibilidad del servidor DESA o ambiente espejo.
  • Accesos y permisos de instalación en el servidor.
  • Definición del modelo piloto a contenerizar.

Supuestos

  • El servidor cuenta con sistema operativo compatible para instalación de Docker.
  • Se dispone del espacio, red y permisos necesarios para ejecutar contenedores.
  • El modelo piloto ya se encuentra funcional en entorno de desarrollo.

Riesgos

  • Restricciones de seguridad o infraestructura para instalar Docker.
  • Dependencias del modelo no declaradas correctamente.
  • Diferencias entre el modelo local y el empaquetado en contenedor.

Definition of Done (DoD)

  • Docker instalado y probado en servidor DESA.
  • Imagen construida exitosamente.
  • Modelo piloto ejecutado dentro de contenedor.
  • Resultados validados con entradas controladas.
  • Documentación técnica almacenada en repositorio o espacio definido.
  • HU validada por referente técnico y usuario responsable.

Tareas técnicas sugeridas

  • Solicitar accesos y permisos al servidor.
  • Instalar Docker y validar servicio operativo.
  • Definir plantilla estándar de proyecto analítico.
  • Generar Dockerfile base.
  • Construir imagen del modelo piloto.
  • Ejecutar pruebas en servidor.
  • Documentar procedimiento técnico.

Formalización del flujo de Fases Tecnicas para Ciencias de Datos

Estado sugerido New / To Do
Como responsable del ciclo de vida del modelo,
quiero formalizar el proceso de promoción DEV-DESA-PROD,
para garantizar validación previa y trazabilidad antes de producción.

Descripción

Para reducir riesgos operativos y asegurar control sobre los modelos analíticos, es necesario definir un flujo formal de promoción entre ambientes. Esta historia establece las reglas mínimas de gobierno para que todo modelo pase por desarrollo, validación técnica y posteriormente producción, con evidencia, responsables y versiones identificables.

Objetivo

Contar con un proceso claro, repetible y auditable de promoción de modelos entre entornos, disminuyendo despliegues manuales o no controlados.

Alcance

  • Definir el flujo oficial DEV → DESA → PROD.
  • Establecer validaciones previas obligatorias antes de producción.
  • Definir responsables, evidencias y puntos de control.
  • Documentar el proceso de promoción y versionado mínimo.
  • Dejar preparado el camino para futura automatización.

Fuera de alcance

  • Automatización completa del despliegue.
  • Monitoreo productivo avanzado.
  • Versionado formal con herramientas especializadas como MLflow.

Criterios de aceptación

  • Se documenta el flujo oficial de promoción de modelos entre DEV, DESA y PROD.
  • Todo modelo debe pasar por una validación técnica previa en DESA antes de su promoción.
  • Se establece formalmente que no habrá ejecuciones directas en producción sin validación previa.
  • La promoción a producción se realiza únicamente con una versión validada del contenedor.
  • Se define un mecanismo formal para registrar evidencia de validación, versión y responsable.
  • El proceso queda preparado para futura automatización mediante jobs o scheduler.

Dependencias

  • Existencia del entorno DESA operativo.
  • Modelo contenido y ejecutable en Docker.
  • Alineación con áreas de infraestructura, seguridad y producción.

Supuestos

  • El equipo acepta una política de promoción formal entre ambientes.
  • El ambiente DESA representa razonablemente el comportamiento técnico previo a PROD.
  • Se dispone de un repositorio o medio para registrar evidencias y documentación.

Riesgos

  • Falta de alineación entre áreas sobre responsabilidades de promoción.
  • Saltos de proceso por urgencias operativas.
  • Documentación incompleta de versiones o validaciones.

Definition of Done (DoD)

  • Flujo DEV → DESA → PROD definido y aprobado.
  • Responsables y puntos de control identificados.
  • Formato de evidencia mínima establecido.
  • Documento o guía operativa disponible para consulta.
  • Proceso socializado con los equipos involucrados.

Tareas técnicas sugeridas

  • Levantar proceso actual de desarrollo y despliegue.
  • Diseñar flujo objetivo de promoción.
  • Definir responsables por etapa.
  • Diseñar formato de evidencia de validación.
  • Documentar política de promoción y restricciones.
  • Socializar el proceso con áreas involucradas.

Conclusión

La HU 1 habilita la base técnica del proyecto con Docker y la contenerización del modelo. La HU 2 establece la base operativa y de gobierno para el paso ordenado entre DEV, DESA y PROD. Juntas constituyen el arranque natural de la épica Proyecto MLOps.
