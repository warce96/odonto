ML Ops y Control de Entornos

Propuesta para fortalecer la reproducibilidad, control operativo y escalabilidad de modelos analíticos

Situación actual

  • Ejecución de modelos en entornos no controlados
  • Dependencias inconsistentes entre equipos
  • Resultados no reproducibles
  • Procesos manuales de despliegue
  • Limitada capacidad de auditoría y trazabilidad
“El modelo daba AUC 0.78 ayer… hoy 0.72”

Escenario de decisión

Modelo actual (sin control estructurado)

  • Dependencia del entorno local
  • Alta variabilidad en resultados
  • Dificultad para replicación
  • Mayor riesgo operativo

Modelo propuesto (Docker + ML Ops)

  • Estandarización de entornos
  • Reproducibilidad garantizada
  • Ejecución controlada
  • Base para automatización y escalabilidad
La adopción de Docker permite establecer las bases de una arquitectura ML Ops, asegurando consistencia, control y trazabilidad en la ejecución de modelos.

El desarrollo se mantiene en entornos locales, mientras que la validación y ejecución productiva se realizan en entornos controlados, asegurando consistencia sin limitar la capacidad de experimentación.

Arquitectura de ejecución

Flujo de promoción de modelos desde desarrollo hasta producción

Ciencia de Datos (DEV)

  • Jupyter Notebook / Python
  • Construcción de modelos
  • Pruebas analíticas
  • modelo.py + requirements.txt
→

Validación (DESA)

  • Servidor Ubuntu
  • Docker build
  • Ejecución controlada
  • Validación técnica
→

Producción (PROD)

  • Contenedor validado
  • Ejecución automatizada
  • Integración con Oracle
  • Resultados operativos
El flujo establece un proceso claro de promoción de modelos: desarrollo analítico → validación controlada → ejecución productiva.

Buenas prácticas recomendadas

  • Separación formal entre desarrollo y ejecución
  • Control estricto de dependencias (requirements.txt)
  • Validación obligatoria en entorno DESA
  • Prohibición de ejecución directa en producción
  • Versionado de modelos y lógica analítica
  • Ejecución centralizada y controlada

Impacto en el equipo de Ciencia de Datos

  • No se modifica el flujo de trabajo actual
  • Continuidad en el uso de Jupyter Notebook y Python
  • Mantenimiento de la flexibilidad analítica
  • Incorporación de prácticas de estructuración del código
  • Formalización del manejo de dependencias
  • Fomento de buenas prácticas de desarrollo y documentación
Este enfoque permite evolucionar hacia un modelo de trabajo más estructurado, sin afectar la productividad del equipo de Ciencia de Datos.

Implementación técnica

  • Disponibilidad de servidor Ubuntu en entorno DESA (espejo de producción)
  • Docker instalado exclusivamente en servidores
  • Proceso de validación previo a producción
  • Ejecución automatizable mediante jobs o scheduler
  • Integración directa con Oracle para consumo y persistencia de datos

Evolución hacia ML Ops

Estado actual

  • Docker como estándar de ejecución
  • Entornos controlados
  • Reducción de variabilidad operativa

Próximos pasos

  • MLflow: versionado y gestión de modelos
  • DVC: versionado de datos y features
  • Automatización de pipelines analíticos
  • Gobierno completo del ciclo de vida del modelo
Docker (entorno) → MLflow (modelo) → DVC (datos)

Impacto en el Area

  • Reducción del riesgo asociado a modelos analíticos
  • Mayor confiabilidad en resultados
  • Capacidad de auditoría y trazabilidad
  • Escalabilidad de soluciones analíticas
  • Base para automatización y decisiones basadas en datos
Conclusión:

La implementación de Docker establece una base sólida para ML Ops, permitiendo evolucionar hacia un modelo de ejecución controlado, reproducible y escalable. La incorporación de MLflow y DVC permitirá completar el ciclo de gobierno de modelos y datos, alineando la analítica con estándares empresariales.
